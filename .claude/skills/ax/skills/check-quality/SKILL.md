# ax: Check Quality

프로젝트 규약(시뮬레이터 기본값, 테스트 타깃)은 리포 루트의 `.claude/ax.md`에 있다. 있으면 **먼저 읽는다.**

## Overview
남아 있는 테스트가 가질 만한 값어치인지 확인한다: 다른 머신에서 추가 설정 없이 돌고, 중복이 없고, 자명한 걸 assert하는 대신 실제 동작을 검증한다.

## When to Use
- `/ax:execute-plans`가 태스크/plan을 끝낸 뒤, `/ax:review-code` 또는 PR 직전.
- NOT: 초기 구현 중의 테스트 작성 — 그건 `/ax:execute-plans` 안의 TDD.

## 실행 방식
`ax:tester` 서브에이전트에 넘길 수 있다 (기계적 정리 + 실행 루프). 프롬프트에는 테스트 타깃 경로와 이번 변경 범위만 준다.

## Rules

1. **단위 vs UI 테스트 구분.** 로직은 단위 테스트, 화면 흐름은 UI 테스트. UI 테스트는 최소한으로 — 느리고 깨지기 쉽다.
2. **다른 PC에서 바로 실행 가능해야 한다.** 특정 시뮬레이터 이름, 디바이스 UUID, 로컬 파일 경로에 하드코딩된 테스트는 실패로 간주. 실행 시 시뮬레이터 지정은 도구 인자로 하되 **테스트 코드 자체가 그 값에 의존하지 않게** 쓴다.
3. **의미 없는 테스트는 삭제한다.** getter/setter 확인, 프레임워크가 이미 보장하는 동작 확인 등.
4. **읽어서는 못 믿는 핵심 경로에 테스트가 없으면 추가한다.** 이 스킬의 주 목적은 나쁜 테스트를 걷어내는 것이지만, 걷어내기 전에 "눈으로 봐서는 맞는지 확인할 수 없는 동작"이 미검증으로 남았는지 한 번 본다 — 취소/종료 전파, 리소스 해제, 동시성 연쇄처럼 **틀려도 컴파일되고 겉보기 동작도 정상인** 것들이다. 판정 기준: **"이 줄을 지워도 기존 테스트가 전부 통과하는가"** — 통과하면 그 줄은 미검증이다. 실제로 취소 전파에 이 기준을 적용해 프로덕션 버그가 드러난 사례가 있다.
   - **미검증 라인을 찾았으면 테스트를 쓰기 전에 그 줄이 옳은지부터 의심한다.** 테스트를 못 쓰겠거나 시나리오가 억지스럽다면 그건 테스트 실력 문제가 아니라 **그 줄이 필요 없거나 틀렸다는 신호**다(실사례: 재시도 Task 취소가 미검증이라 테스트를 짜다가, 그 취소가 도달 불가능한 경우를 막으면서 정상 경로를 깨고 있었음이 드러났다 — 줄을 지우는 것이 수정이었다).
5. **중복 테스트는 통합하거나 삭제한다.** 같은 케이스를 이름만 바꿔 두 번 두지 않는다.
6. **검증은 실제 실행으로.** 로직은 `mcp__XcodeBuildMCP__test_sim`, UI 동작(탭·스크롤·펼침 등 상태 변화)은 `tap`/`snapshot_ui`/`screenshot`으로 실제 돌려 확인 — "코드상 맞아 보인다"로 끝내지 않는다.

## Quick Reference

| 신호 | 조치 |
|---|---|
| 테스트가 특정 시뮬레이터/디바이스 이름을 하드코딩 | 제거하거나 파라미터화 |
| outcome이 아니라 구현 디테일(private 프로퍼티 등)을 assert | 재작성 또는 삭제 |
| 같은 시나리오를 커버하는 테스트가 2개 이상 | 하나로 통합 |
| UI 테스트가 단위 테스트로 커버 가능한 로직을 검증 | 단위 테스트로 이동, UI 테스트 삭제 |
| UI 동작(탭/스크롤/애니메이션)을 텍스트 assert만으로 검증 | 실제 실행해서 확인 |

## Common Mistakes
- 커버리지 숫자를 올리려 의미 없는 assert 추가 — 오히려 삭제 대상.
- `test_sim`을 안 돌리고 "테스트 작성 완료"로 보고 — 실행해서 통과를 확인해야 완료.
- UI 동작 변경을 코드 리뷰만으로 "확인 완료" 처리 — 시뮬레이터에서 실제로 탭/스크롤해야 완료.
- MCP 도구가 안 잡히거나 시뮬레이터가 이상하게 굴면 앱 코드 문제로 단정하지 말 것 — 호스트/캐시 문제일 수 있다. 프로젝트의 함정 문서(`.claude/ax.md`가 가리키는 곳)를 먼저 본다.

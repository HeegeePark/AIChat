# 함정 사전

이 프로젝트에서 실제로 한 번씩 물렸던 것들. **매 세션 읽을 필요는 없고**, `CLAUDE.md`의 인덱스가 가리키는 절만 해당 작업 직전에 읽는다. 새 교훈은 "증상 → 대처" 한 줄로 해당 절에 추가한다.

## Swift 동시성

- **`nonisolated struct`로 선언해도 프로토콜 요구사항을 구현한 메서드는 MainActor 격리로 남는다.** 프로젝트 기본 격리가 MainActor(`SWIFT_DEFAULT_ACTOR_ISOLATION`)인데 프로토콜 선언에 `nonisolated`가 없으면, 그 프로토콜을 준수하는 `nonisolated struct`의 메서드도 nonisolated 컨텍스트에서 부르는 순간 "main actor-isolated instance method 'X' cannot be called from outside of the actor" 경고가 난다(Swift 6에서는 에러). 타입에 붙인 `nonisolated`나 `static let`에 붙인 `nonisolated`로는 안 없어진다 — 실제로 `static let`을 의심해 고쳤다가 헛수고했다. 해결은 둘 중 하나: **호출부를 같은 격리로 맞추거나**(테스트 타입에 `@MainActor`), 서비스가 정말 액터에서 자유로워야 하면 **프로토콜 선언 자체를 `nonisolated`로** 바꾼다.
  - 진단이 **호출부마다 다르게 뜨는 게 함정이다**: `try await f(service.greeting())`처럼 이미 `await` 표현식 안에서 호출하면 경고가 안 나고, `let x = service.send(...)`처럼 await 없는 동기 문장에서만 난다. "이 메서드만 문제인가?" 하고 메서드 구현을 뜯어보게 되는데, 원인은 메서드가 아니라 **호출 지점의 격리**다.
- **`nonisolated` 타입 안에 non-Sendable 클래스를 `static let`으로 캐시하려 하면 격리가 호출부와 테스트까지 번진다.** `RelativeDateTimeFormatter`·`DateFormatter` 같은 Foundation 포맷터가 대표적이다 — 전역 상수로 두려면 `@MainActor` 같은 격리를 명시해야 하는데, 그러면 그걸 읽는 `static func`도 격리돼야 하고 결국 테스트 타입에까지 `@MainActor`가 붙는다(`Utilities/`의 다른 타입들은 전부 `nonisolated enum`인데 하나만 튀는 상태가 된다). **호출 빈도가 낮으면 인스턴스를 호출마다 만드는 쪽이 코드가 더 짧다** — `RelativeTime`은 화면에 보이는 말풍선당 1분에 한 번 호출이라 생성 비용이 무의미해서 캐시를 버렸다. 캐시가 정말 필요한 빈도라면 그때 격리를 감수한다.
- `@MainActor` 격리된 타입의 `init` 기본 파라미터 값으로 그 타입의 `static let`(예: mock 데이터)이나 다른 `@MainActor` 격리 타입의 `init()` 자체(예: `ChatViewModel.init(service: ChatService = MockChatService())`)를 참조하면 "main actor-isolated ... can not be referenced from a nonisolated context" 경고/에러가 난다 — 기본 파라미터 값은 호출부 컨텍스트에서 평가되어 액터 격리를 상속받지 않기 때문. `static let`은 `nonisolated`를 명시하고, 타입 자체를 참조하는 경우엔 그 타입 전체를 `nonisolated struct ... : Sendable`로 선언한다(프로퍼티가 모두 불변값이면 안전).
- **`@MainActor` + `@Observable` 클래스의 `deinit`에서 `Task` 핸들을 cancel하려면 저장 프로퍼티 isolation을 풀어 줘야 한다.** MainActor-isolated 프로퍼티를 deinit에서 읽으면 "main actor-isolated property ... can not be referenced from a nonisolated context". `@ObservationIgnored` + `nonisolated(unsafe)`(또는 동등)로 **핸들만** 빼고, mutation·`persist`는 deinit에 넣지 않는다. 순수 `nonisolated var`는 Observation 매크로가 추적 저장 프로퍼티로 바꿔 **컴파일 에러**가 난다(`greetingTask`).
- **`UIViewRepresentable` Coordinator + UIScrollView KVO**는 콜백이 nonisolated인데 모듈 기본이 MainActor라, `self.evaluate()`를 직접 부르면 “call to main actor-isolated … in a synchronous nonisolated context”가 난다. 스크롤 틱마다 `Task { @MainActor in … }`를 만들면 경고는 없어져도 플링 중 Task가 폭주한다. **패턴**: KVO 진입을 `nonisolated` 스케줄로 두고 `DispatchQueue.main.async` 한 홉 뒤 `MainActor.assumeIsolated { evaluate() }` (`ScrollViewBottomObserver`).

## 비동기 · 디바운스

- **디바운스와 서비스 지연은 호출 경계로 구분한다.** 전송 파이프라인은 `service.send` 전 300ms quiet를 명시적으로 기다리고, `MockChatService.delay`는 호출 후 첫 청크까지의 TTFT만 담당한다. 두 지연이 직렬로 보이는 것은 의도된 계약이며, 서비스 내부 지연을 다시 디바운스 취소 창으로 사용하면 요청 전 대기와 요청 후 TTFT가 결합돼 실서버 교체 시 동작이 달라진다. 취소로 인한 `CancellationError`와 그 외의 실제 실패도 반드시 분기한다 — 취소는 더 최신 작업이 상태를 이어받는 정상 경로지만, 실제 실패는 아무도 치워주지 않으므로 그 자리에서 상태를 복구해야 한다.
- **디바운스 테스트에서 `send()` 직후 `callCount == 0`만으로 quiet 경계를 증명하지 않는다.** sleep을 지워도 `Task`의 비동기 실행 홉 때문에 동기 단언 시점에는 아직 서비스가 안 불려 테스트가 통과할 수 있다. 서비스 첫 호출 시각을 기록해 `send`부터 주입 interval 이상 지났는지 단언하고, 타이머 리셋은 두 번째 `send` 시각부터 interval 전체가 다시 경과했는지 별도로 잰다.

- **`AsyncStream`/`AsyncThrowingStream`은 소비 Task가 `next()`에서 취소를 관측할 때만 종료된다.** standalone Swift로 측정한 결과:
  | 상황 | `onTermination` 발화 |
  |---|---|
  | `for await` 루프를 `break`로 탈출 | **안 됨** |
  | 소비 `Task`를 `cancel()` (next()에서 대기 중) | 됨 |
  | 스트림 값의 참조 해제(deinit) | 됨 |

  그래서 **스트림을 소비하는 루프 안에서 `try await Task.sleep`이 취소로 throw하면 상류가 안 멈춘다** — `next()`를 거치지 않고 루프 밖으로 빠져나가기 때문이다. 프로듀서가 계속 돌아 누수가 되고, 디바운스로 취소해도 실질적으로 취소되지 않는다. 취소를 `try?`로 삼키고 `if Task.isCancelled { break }`로 루프 꼭대기(`next()`)에 돌려보내야 거기서 취소가 관측되어 상류까지 연쇄 종료된다(`TypewriterStream` 실사례). 스트림을 감싸 변환하는 코드에서는 `continuation.onTermination`에 내부 `Task.cancel()`을 잇는 것만으로 부족하고, 이 지점까지 봐야 체인이 완성된다.

  검증할 때 `break`로 소비를 멈추는 테스트를 쓰면 위 표의 1행 때문에 **프로덕션 코드가 맞아도 실패한다** — 실제 취소 경로와 같게 소비 `Task`를 `cancel()`해야 한다.

- **`Task.sleep`으로 페이싱할 때 지연을 10ms 밑으로 줄이는 방식은 안 먹는다** — 오차가 지연 자체만큼 크다(실측: 4ms 목표가 실효 ~10ms로 나와, 300자를 1.2초에 끝낼 계산이 3.2초 걸렸다). 더 빠르게 흘려야 하면 **틱 간격을 줄이지 말고 틱당 처리 개수를 늘린다**(`TypewriterStream`의 backlog 비례 batch). 덤으로 sleep 호출 횟수가 줄어 부하도 낮다.
- **동시 재시도 회귀 테스트에서 `text.contains("A")`만 보면 사용자 말풍선 `"A"`에 바로 통과한다.** AI 응답 완료를 보려면 `sender == .ai`를 AND 한다 — 안 그러면 “둘 다 완료” 단언이 스트리밍 전에 성공하고, 맵 정리 assert가 플레이크/거짓 실패한다.
- **ViewModel이 `Task { self… }`로 장수명 작업을 필드에 보관하면 `self → Task → self` 사이클이 생긴다.** 진행 중엔 외부 소유를 끊어도 `deinit`이 안 불려 `deinit` cancel이 무력하다. `Task { [weak self] in … }`로 끊는다. 다만 `guard let self` 이후 본문이 돌면 그 구간은 다시 강하게 붙잡히므로, **in-flight 관측 테스트는 `_ = ChatViewModel(...)`로 바로 버리면 안 된다** — 폴링 클로저 등에서 VM을 읽어 수명을 연장한다(`HangingChatService` greeting in-flight). “이 줄을 지워도 테스트가 통과하는가”로 cancel-on-send 같은 핵심 취소를 한 번 확인하면 회귀 테스트가 허수인지 바로 드러난다.
- **취소 여부는 스트림 read 결과가 아니라 actor 정착 직전에 다시 판정한다.** read가 `.completed`/`.failed`를 반환해도 다음 `MainActor` hop 전이나 다중 스트림 사이에 stop·supersede가 Task를 취소할 수 있다. 정착 시 `Task.isCancelled`를 반영한 effective outcome을 쓰고, 취소된 모든 loop exit에서 **아직 active인 현재 run key만** 정확히 닫는다. 이미 terminal failure로 active 집합에서 빠진 키까지 지우면 재시도 원본이 사라진다.
- **인사말 hang + 응답 완료를 같이 보려면 mock이 greeting과 send를 둘 다 hang하면 안 된다.** `HangingChatService`는 둘 다 안 끝나 응답 완료 단언이 영원히 실패한다. greeting만 hang(또는 prefix 후 hang)·`send`는 즉시 성공하는 더블을 쓴다(`HangingGreetingInstantSendService`).
- **부분 인사 텍스트를 한 청크 문자열 통째로 단언하지 말 것.** `TypewriterStream`이 청크 마지막 1글자를 다음 청크/종료까지 보류하므로, hang 전에 청크 하나(`"안녕"`)만 주면 화면에 일부만 보이거나 기대 전체가 안 잡힌다. 청크를 둘 이상으로 나누거나 “비어 있지 않음”으로 폴링한다.
- **grapheme 경계 보호로 "다음 청크까지 보류"한 마지막 글자는, 상류가 에러로 끊길 때도 finish 전에 방출해야 한다.** throw만 전파하고 held를 버리면 부분 실패 말풍선에서 마지막 글자가 빠진다. "업스트림 에러가 전파된다" 테스트만 있으면 이 줄은 **지워도 통과**한다 — held flush 후 throw를 별도로 고정한다(`TypewriterStream`).
- 스트림 변환에서 "얼마나 밀렸는지"를 알아야 하면 소비 속도에 맞춰 상류 `next()`를 부르는 구조로는 불가능하다 — 밀린 양이 `AsyncStream` 내부 버퍼에 숨는다. 흡입(상류를 지연 없이 빨아들임)과 방출(페이싱)을 **두 Task로 갈라** 공유 카운터로 잇는다. 공유 값이 `Int` 하나뿐이면 actor 대신 `OSAllocatedUnfairLock`(iOS 16+, `Sendable`)이 가볍다. 이때 취소 전파는 `continuation.onTermination`에서 **두 Task를 모두** 취소해야 완성된다.
- **표준 라이브러리만 쓰는 의미론 질문(동시성·문자열·Unicode 등)은 시뮬레이터로 왕복하지 말고 standalone Swift로 격리 측정한다.** `swift probe.swift` 한 번이 2초인데 `test_sim`은 40초라, 가설을 여러 개 재볼 때 차이가 크다. 위 `AsyncStream` 표도 이렇게 얻었다. 방법: 스크래치패드에 단계별 플래그(`final class Flag: @unchecked Sendable` + `NSLock`)를 심은 최소 재현을 쓰고 `swift <파일>` 실행 → 어느 단계에서 체인이 끊기는지 한 번에 보인다. UIKit/SwiftUI가 안 얽힌 코드에만 쓸 수 있다.

## SwiftUI 레이아웃

- `ScrollViewReader`의 `proxy.scrollTo(id:)`를 `@Observable` 상태를 방금 mutate한 것과 같은 동기 호출 프레임에서 곧바로 부르면 조용히 실패한다 — 상태 변경이 다음 런루프에서 반영되므로 아직 레이아웃 안 된 행을 찾는 셈이다. 최소 한 프레임(`Task.sleep(for: .milliseconds(16))` 등, 1ms처럼 너무 짧은 값은 렌더 사이클과 동기화가 안 돼 다시 실패할 수 있다) 또는 `DispatchQueue.main.async`로 한 틱 미룬 뒤 호출한다. 또한 `anchor: .top`은 대상 뒤에 남은 콘텐츠가 뷰포트 높이보다 짧으면(마지막 행이고 응답 전일 때 특히) `ScrollView`가 바닥에서 clamp되어 상단까지 못 올라가므로, 리스트 끝에 `GeometryReader`로 잰 뷰포트 높이만큼 `Color.clear` 스페이서를 둬서 항상 스크롤할 여지를 확보한다.
- 화면 전체(입력창 포함)를 `GeometryReader`로 감싸면 키보드가 뜰 때 입력창이 함께 밀려 올라가는 SwiftUI 기본 키보드 회피 동작이 깨진다 — `GeometryReader`는 그 측정값이 실제로 필요한 뷰(예: `ScrollView`)만 좁게 감싸고, 키보드에 반응해야 하는 형제 뷰(입력창 등)는 감싸지 않는다.
- `HStack { Spacer(minLength:); 내용View }`처럼 `Spacer`로 한쪽 끝에 앵커링하는 구조에서, 그 "내용 View" 하나에만 조건부로 padding을 추가/제거해 장식(예: 말풍선 꼬리) 공간을 확보하면 안 된다 — 조건에 따라 frame 폭이 달라지면 `Spacer`가 반대쪽 여백을 흡수해 형제 요소들과 정렬이 어긋난다. 여백을 예약해야 하면 조건과 무관하게 항상 동일하게 적용하거나, 애초에 frame 크기를 안 바꾸는 방식(예: 아래 `UnevenRoundedRectangle`)을 우선 고려한다.
- 모서리 하나만 다른 radius를 갖는 뾰족한/장식적 모서리가 필요하면(말풍선 꼬리 등) 커스텀 `Shape`+`Path`로 직접 그리기 전에 표준 `UnevenRoundedRectangle`(iOS 16+)부터 검토한다 — 4개 모서리 radius를 개별 지정할 수 있어 코드가 훨씬 짧고, frame 크기를 전혀 바꾸지 않아 위 정렬 문제 자체가 발생하지 않는다.
- `HStack`에 긴 `Text`와 짧은 `Text`를 나란히 두면 남는 폭을 **반씩** 나눠 긴 쪽이 절반에서 잘린다. 폭을 보장해야 하는 쪽(레이블·버튼 등)에 `.layoutPriority(1)`을 줘 이상적 폭을 먼저 확보하게 하고 나머지를 긴 쪽이 쓰게 한다. 이 구조는 "예약 폭을 미리 계산해 문자열을 자르는" 방식보다 안전하다 — 폭 배분을 레이아웃이 하므로 측정 오차가 겹침으로 번지지 않는다.
- 뷰가 100줄을 넘었는데 초과분이 실제로는 View가 아니라 조건부 스타일 계산(예: 발신자별 색상/밑줄 분기)이면, CLAUDE.md의 "하위 뷰로 추출" 원칙을 문자 그대로 따라 억지로 자식 `View`를 만들 필요는 없다 — 그 로직이 특정 모델 타입(예: `Message.Sender`)에 종속적이면 `struct { ... }` 바깥에 그 타입의 `private extension`으로 빼는 편이 더 적합하다. View struct 라인 수도 줄고, "이 스타일이 무엇에 속한 개념인가"가 타입 이름으로 드러나 관심사 분리도 더 명확해진다(`MessageBubble.swift`의 `Message.Sender` 확장 참고).
- `GeometryReader`+`PreferenceKey`로 스크롤 위치(예: 최하단 여부)를 추적할 때, 그 마커 뷰(또는 `.background(GeometryReader)`)를 `LazyVStack` 안에 두면 화면 밖으로 스크롤되는 순간 지연 렌더링 때문에 `preference`가 더 이상 갱신되지 않는다(실측: `onPreferenceChange`가 이후로 한 번도 안 불림). **마커를 Lazy 안에 두지 말 것** — `onAppear`/`onDisappear`로 우회할 수 있다고 착각하지 말 것(이 콜백은 스크롤 "뷰포트 가시성"이 아니라 뷰 identity의 mount/unmount라서, `VStack`으로 바꿔도 스크롤 중엔 트리거되지 않음, 실측). **현재 해결(Lazy 복구)**: 목록은 `LazyVStack`, 최하단 판정은 UIScrollView contentOffset 관찰(`ScrollViewBottomObserver` + `ScrollBottomDetector` 순수 함수). Preference 마커 경로 폐기. 전송용 뷰포트 높이 스페이서는 Lazy+`.padding()` **밖**에 두고, contentSize에 들어간 그 높이만 `trailingSlack`으로 메시지 끝 기준 최하단에서 뺀다. `adjustedContentInset.bottom`은 max offset에 더해지므로 distance 식에서는 **더한다**(빼면 inset 있을 때 중간 스크롤을 바닥으로 오판).
- `onPreferenceChange` 등으로 `GeometryReader` 파생 상태를 실시간 갱신할 때, 레이아웃이 아직 안 끝난 첫 패스(`geometry.size.height == 0`)에서 판정하면 항상 틀린 값이 나와 상태가 `true→false`(또는 반대)로 잠깐 뒤집혔다가 다음 패스에서 다시 돌아오는 깜빡임이 매 런치마다 재현된다(실측: 두 콜백이 35ms 간격으로 발동, `withAnimation` 진행 중에 반전). `size.height > 0` 같은 가드로 미측정 구간의 판정을 건너뛰면 해결된다.
- **전송용 뷰포트 높이 스페이서를 “메시지 끝 마커”처럼 쓰지 말 것.** contentOffset 최하단 판정은 content **절대 끝**을 본다. 스페이서를 Lazy+padding **안**에 두면 spacing·padding bottom이 slack 밖으로 남아 `scrollTo(last, .bottom)` 직후에도 버튼이 남을 수 있다(실측·리뷰). 스페이서는 목록 padding 밖 형제로 두고 `trailingSlack` = 그 높이만 쓴다.
- **"스트리밍 중 스크롤 하단 자동 고정"은 이 프로젝트에서 의도적으로 구현하지 않는다(미구현 종료).** 전송 시 2단계 스크롤이 사용자 메시지를 최상단에 고정해 답변에 빈 화면을 통째로 내주므로 뷰포트 이내 답변은 추적 없이 전부 보이고, 넘치는 경우는 하단 이동 버튼이 담당한다. 자동 고정을 얹으면 사용자 메시지 상단 고정 연출이 깨지고, 글자마다 `scrollTo`가 `ScrollView` 자체 애니메이션과 겹쳐 떨림이 된다. GPT/Claude/Gemini/Grok 모두 같은 이유로 자동 고정 대신 버튼만 제공한다. Preference 마커 시절에는 VStack 안 마커가 스트리밍 성장에도 갱신됐지만, **현재는 offset/contentSize KVO**라 Lazy여도 contentSize 변화 시 재평가된다 — Preference 마커로 되돌리지 말 것.
- **anchor: .top용 뷰포트 높이 스페이서를 상시 존재시키지 말 것(QA 리포트: 최하단에서 자유 드래그로 빈 화면까지 내려감, 재현: 반복적으로 위로 올렸다가 최하단으로 스크롤 다운).** 위의 뷰포트 높이 스페이서는 "방금 보낸 메시지를 top으로 스크롤할 여지 확보"가 목적인데, 그 여지가 항상 뷰포트 높이만큼 켜져 있으면 `trailingSlack`이 버튼 판정에서는 잘 제외되더라도 **실제 드래그 스크롤 자체는 그 빈 공간까지 들어간다** — content 절대 끝이 메시지보다 한 화면 더 밑에 있기 때문에 바운스가 아니라 진짜로 멈춰 선다. 해결: 스페이서 높이·`trailingSlack` 조건을 새 `@State` 없이 **이미 있는 `postSendTopAnchorID != nil`**(열린 전송 배치 동안만 non-nil, `.onChange(of: hasPendingSendBatch)`가 배치 종료 시 자동으로 nil 복귀)로 대체한다 — 새 플래그를 추가하면 `ChatView`가 SwiftLint `type_body_length`(250줄) 문턱을 넘는다(실측: 252줄, 기존 상태를 재사용하는 쪽이 더 작은 diff이자 통과 경로). 검증 시 주의: "몇 번 보냈는지"보다 **isAtBottom이 이미 true인 채로(하단 이동 버튼이 안 뜬 채로) 자유 드래그하는 경우**를 재현해야 한다 — 버튼을 눌러 `anchor: .bottom`으로 명시 스크롤하면 offset이 그 호출로 다시 유효해져 버그가 가려진다.

- **부모 body 무효화 ≠ 모든 자식 body 재평가.** `@Observable` 프로퍼티를 건드리면 그걸 읽는 뷰의 body가 다시 도는 건 맞지만, 자식은 **View 값 비교로 걸러진다** — 저장 프로퍼티가 안 바뀐 자식은 body가 다시 불리지 않는다. 단, **저장 프로퍼티에 클로저가 하나라도 있으면 이 필터가 통째로 무력화된다** — 캡처가 같아도 컨텍스트 박스가 매번 새로 할당돼 구조 비교가 항상 불일치한다. 그래서 "값 비교로 걸러지겠지"를 전제로 깔지 말고 **뷰마다 계측으로 확인한다**. ~~말풍선 10개 대화에서 스트리밍 중인 말풍선 하나만 재평가되더라~~는 이전 기록은 **반증됐다**: `MessageBubble`이 `onExpand: () -> Void`를 들고 있어 글자마다 화면의 **모든** 말풍선이 전체 텍스트를 다시 조판했다(실측 2500자: `shouldCollapse` 2,300회/21.7초, 20fps). `Equatable` 수동 구현 + `.equatable()`을 붙여 클로저를 비교에서 빼자 0회/59fps가 됐다(클로저가 비교 대상 값 밖의 상태에 의존하게 되면 이 계약이 깨지므로 주석으로 못 박아 둔다). "리스트 원소 하나를 바꾸면 전체가 다시 그려진다"도, 그 반대도 단정하기 전에 **계측부터 한다** — 계측 방법은 뷰의 계산 프로퍼티에서 `Logger(subsystem: bundleId, category:)`로 id별 호출 횟수를 찍고 `osLogPath`를 grep(「화면 검증」 참고).
  - 이 프로젝트에서 실제로 이 단정을 사실처럼 리뷰에 적었다가, 확인해보니 문제가 없었던 사례가 있다. **외부 문서·기사에서 읽은 성능 주장을 리뷰 findings로 옮길 때는 전제를 직접 검증하고, 검증 못 했으면 "미검증 가정"이라고 명시한다.** 맞는 세부 사실 몇 개(단위 비용, 내부 호출 경로)가 틀린 결론을 그럴듯하게 받쳐줄 수 있다.

- **`UIViewRepresentable.updateUIView`는 값이 그대로여도 불린다.** SwiftUI의 값 비교 스킵은 여기까지 보장되지 않으므로, 안에서 `attributedText` 같은 걸 무조건 다시 대입하면 내용이 같아도 전체 재조판·재드로우가 일어난다. 길이에 비례하는 작업을 품은 래퍼는 **마지막으로 반영한 입력을 라벨에 들고 있다가 같으면 조기 반환**한다(`IntrinsicHeightLabel.Applied`). `String` 비교는 같은 인스턴스면 포인터 비교로 끝나 길이와 무관하다.
- **`intrinsicContentSize`는 한 번 갱신에 여러 번 질의된다.** Auto Layout과 SwiftUI 사이징이 각각 물어봐 실측상 정확히 2회 돌았다. 그 안에서 `sizeThatFits`처럼 비싼 계산을 하면 그대로 2배다 — 입력이 바뀔 때만 버리는 캐시를 둔다. 다만 두 번째 호출은 TextKit 내부 캐시가 받아줘서 **절반이 아니라 20% 정도** 준다(실측 5.4s → 4.3s). 캐시로 회당 비용이 올라 보이는 건 원래 비용이 드러난 것이지 나빠진 게 아니다.
- **`dynamicTypeSize.isAccessibilitySize`를 "한 줄에 들어가는가"의 대용으로 쓰지 말 것.** 접근성 크기(AX-*)에서만 세로 배치로 넘기면 **그 직전 단계인 `xxxLarge`가 통째로 미검증 구간으로 남는다** — 실측에서 AX-3XL은 멀쩡한데 `xxxLarge`에서 캡션이 화면 밖으로 잘렸다. 임계값을 상수로 박는 대신 `ViewThatFits(in: .horizontal)`에 후보 두 개(한 줄 배치 / 세로 배치)를 주고 레이아웃이 실제 폭으로 고르게 한다. 글자 크기뿐 아니라 기기 폭·라벨 길이("방금 전" vs "11개월 전")까지 한꺼번에 반영된다. 검증할 때도 `large`와 `AX-*`만 보지 말고 **그 사이 단계 + 가장 긴 라벨** 조합을 함께 본다.
- **`ViewThatFits` 후보 안에 `Spacer`가 있으면 언제나 "들어간다"고 판정된다** — `Spacer`가 부모 제안만큼 폭을 늘려버려 첫 후보가 늘 선택되고, 정작 넘치는 콘텐츠는 그대로 잘린다. 한쪽 끝 앵커링용 `Spacer`는 후보 **바깥**(부모)으로 빼거나, 후보를 구성하는 하위 뷰가 `Spacer`를 품지 않게 만든다(`MessageBubble`에서 `Spacer`를 걷어내 말풍선만 그리게 하고 행 조립을 `ChatView`로 옮긴 이유).
- **행 `HStack`이 `.bottom` 정렬이면, 그 안의 자식 하나를 세로로 키우는 순간 형제(아바타 등)가 같이 끌려 내려간다.** 말풍선 아래에 뭔가(재시도 버튼, 시간 캡션)를 붙일 일이 생기면 말풍선 뷰 **안**이 아니라 행을 소유한 부모에서 붙인다. 이 규칙을 어기면 아바타가 말풍선이 아니라 그 아래 캡션 옆에 정렬된다.

## SwiftUI 접근성

- **입력 `TextField`에 identifier만 있고 제목·label이 비면** VoiceOver가 필드 목적을 전달하지 못한다. 시각 placeholder와 VO `accessibilityLabel`을 **역할별로 분리**한다(예: label「메시지」, placeholder「메시지 입력」). `snapshot_ui`에서 `text-field|메시지|메시지 입력|messageInput`처럼 label/value/id가 같이 보이는지로 확인한다.
- **전송 비활성 사유 hint는 “빈 입력”만 이번 범위로 둔다.** `canSend`가 배치 상한 등으로도 false가 될 수 있으니, hint 조건은 `입력이 공백 제거 후 empty`일 때만 걸고 배치 사유까지 한 문자열에 섞지 않는다.
- **빈 실패 말풍선을 완료 답변과 구분할 때** 표시 문구(`MessageFailureCopy`)는 유지하고, VO 전용으로 `accessibilityValue`에 「실패」 같은 짧은 맥락을 붙이는 편이 UITest 원문 라벨 조회를 덜 깨뜨린다. label을 다른 문자열로 바꾸면 TimeoutRetry 등 실패 문구 조회가 어긋날 수 있다.
- `.accessibilityElement(children: .combine)`을 건 하위 트리에 `Button` 등 인터랙티브 컨트롤이 들어 있으면, VoiceOver는 그 서브트리 전체를 레이블 하나짜리 **읽기 전용 텍스트**로 합쳐버린다 — 버튼의 레이블 문자열은 읽히지만 탭(활성화)은 안 된다. 텍스트 여러 조각을 한 번에 읽히게 결합하고 싶으면서 그 옆에 별도로 탭 가능한 컨트롤도 둬야 한다면, `.combine`을 형제 전체(컨트롤 포함)에 걸지 말고 텍스트 조각들만 별도로 두거나(합쳐 읽히는 대신 여러 정지 지점으로 나뉘는 것을 감수), 텍스트만 숨기고 별도의 보이지 않는 접근성 레이블 요소를 추가하는 방식을 검토한다. `CollapsedBubbleText`에서 "더 보기" `Button`을 넣으면서 기존 `.combine`을 제거한 사례 참고 — 버튼이 별도 접근성 요소로 노출되는지는 `snapshot_ui`의 `targets` 목록에 그 버튼이 `text` 형제와 분리된 `tap|button` 항목으로 나오는지로 검증한다.
- **과도 상태(대기·로딩 등)를 그 상태에서만 존재하는 별도 접근성 요소로 노출하면, 상태가 끝나는 순간 그 요소가 사라져 VoiceOver 포커스가 화면 최상단으로 튄다.** 상태가 바뀌어도 **같은 요소가 살아남고 레이블만 바뀌게** 만든다 — 대기와 스트리밍을 통틀어 부모 뷰에 `.accessibilityElement(children: .ignore)` + 고정 레이블을 걸고, 완료된 뒤에만 자식(내용·버튼)을 노출하는 식(`MessageBubble`의 `InProgressAccessibility`). 조건부로만 접근성 모디파이어를 걸어야 하면 `if`로 분기하는 `ViewModifier`를 쓴다 — `.accessibilityLabel("")`을 삼항으로 넘기면 완료 상태의 레이블까지 지워진다.
- 텍스트 옆에 놓이는 **고정 pt 도형**(점 인디케이터, 배지 등)은 Dynamic Type에서 같이 안 커진다 — 컨테이너 높이를 `UIFont.preferredFont(...).lineHeight`로 잡아두면 큰 글자 설정에서 도형만 상대적으로 쪼그라든다. `UIFontMetrics.default.scaledValue(for:)`로 크기·간격·폭을 함께 스케일하고, 그 뷰가 `@Environment(\.dynamicTypeSize)`를 읽어 재계산되게 한다(`TypingIndicator`).
- **Reduce Motion은 “애니를 제품에서 없앤다”가 아니라 시스템 설정 On일 때만 장식 모션을 줄인다.** Off(대부분 사용자) 경로는 의도 애니를 유지한다. 스펙·리뷰 때 “버튼 슬라이드를 지운다”로 읽히면 먼저 On/Off 분기를 확인한다.
- **`#Preview`에서 `.environment(\.accessibilityReduceMotion, true)`는 빌드가 깨질 수 있다** — 키가 `WritableKeyPath`가 아니라 `KeyPath`로만 잡히는 툴체인/SDK가 있다. Preview 주입 대신 시뮬레이터에 설정을 켠 뒤 앱을 재실행해 검증한다.

## 테스트 실행 · 플레이크

- **`AIChatUITests` 타깃이 `project.pbxproj`에만 있고 소스 폴더가 비어 있으면 표준 전체 `xcodebuild test`가 실패한다.** 단위 테스트만 `-only-testing:AIChatTests`로 돌려 통과시켜도 CI의 전체 Test 액션 실패는 숨긴다. 복구는 타깃을 지우거나 스킵하는 게 아니라 **의미 있는 XCUITest 소스**를 두는 것이다(file system synchronized group이라 `AIChat/AIChatUITests/*.swift` 추가만으로 번들에 포함, `.pbxproj` 편집 불필요). 현재: 전송 스모크, 펼침·timeout 재시도.
- **`accessibilityIdentifier`/`accessibilityLabel` 배선만 추가했을 때 단위 테스트를 억지로 붙이지 않는다.** 그 줄을 지워도 기존 스위트는 통과하지만, outcome을 assert할 수 있는 단위 경계가 거의 없고 프레임워크 보장이 크다. plan이 `snapshot_ui`/`wait_for_ui`로 트리 분리·탭을 이미 DoD로 잡았고 본편 UITest가 후속 이슈면 **추가 단위 테스트 없이 게이트를 닫는다**.
- **`TextField(_:text:axis: .vertical)`은 접근성 트리에서 `textFields`가 아니라 `textViews`로 잡히는 경우가 있다.** XCUITest에서 `app.textFields["id"]`만 보면 `waitForExistence`가 실패한다 — 같은 식별자로 `textViews` 폴백을 두거나, 둘 중 존재하는 쪽을 고른다(`UITestSupport.messageInput`).
- **XCUITest 입력도 `typeText` 대신 pasteboard + Command-V를 쓴다.** `UIPasteboard.general.string = text` 후 `element.typeKey("v", modifierFlags: .command)`로 붙이면 호스트 IME가 영문 QA 토큰까지 한글 자모로 바꾸는 문제를 피한다. 짧게 지나가는 stop/streaming 상태는 고정 sleep을 늘리지 말고 긴 DEBUG QA fixture로 유지한 뒤 실제 버튼 tap과 후속 상태를 단언한다.
- **말풍선 텍스트 XCUITest 조회는 원문 라벨을 쓴다.** 렌더는 `UILabel` + `.byCharWrapping`이라 ZWSP를 넣지 않는다. 개행이 있는 장문은 접근성 트리가 개행을 공백으로 정규화할 수 있으므로 `label == 원문 OR label == 개행→공백` 정도만 허용하고, 부분 매칭·좌표 탭으로 우회하지 않는다.
- **같은 `accessibilityIdentifier`가 화면에 둘 이상이면 `app.buttons["id"].tap()`이 ambiguous match로 실패한다.** 장문 전송 후 mock 에코로 사용자·AI 말풍선이 둘 다 접히면 `moreButton`이 2개다 — `buttons.matching(identifier:).firstMatch`로 순차 탭하거나 count를 본다. 단일 원소 서브스크립트 탭을 쓰지 않는다(`ExpandUITests`).
- **펼친 말풍선은 줄 단위 요소가 아니라 원문 전체 UILabel 하나다.** 접힌 동안 잘려 있던 “마지막 줄 토큰”만 `staticTexts[token]`으로 찾으면 실패할 수 있다 — 펼침 DoD는 **전체 본문** 라벨 존재로 잡는다. 토큰을 마지막 줄에 두는 건 접힘 유도용이지, 펼침 후 단독 조회용 식별자가 아니다.
- **timeout·저장 누출 UI 회귀는 앱 프로세스 안 double + launch argument로 격리한다.** `AIChatTests`의 `FailingChatService` 등은 앱 타깃에 없으므로 UITest가 못 쓴다. `-ui-testing`으로 전용 `UserDefaults` suite를 비우고 지연 0 Mock/`characterDelay: .zero`를 주입하고, timeout 시나리오는 `-ui-testing-timeout-once`로 **첫 `send`만 즉시 `.timeout` throw**(실제 idle 10초 대기 금지). 프로덕션 `MockChatService` 기본 지연·timeout 상수는 바꾸지 않는다(`UITestingBootstrap`).
- **UITest 타깃과 앱 타깃 사이 launch arg 문자열은 리터럴 중복이 정상이다.** 공유 모듈 없이 양쪽에 같은 `"-ui-testing"` 등을 둔다 — 한쪽만 고치면 조용히 기본 경로로 떨어져 격리가 깨진다. 식별자(`retryButton` 등)도 동일 규칙.
- **`test_sim`을 인자 없이 돌리면 UI 테스트가 단위 테스트와 병렬로 클론 시뮬레이터에서 돈다**(UI 테스트 하나가 30초 넘게 머신을 점유). 이때 고정 `Task.sleep` 예산에 기대는 단위 테스트가 간헐적으로 깨진다(실측: 50ms 예산 테스트 2개가 전체 실행에서만 실패, `-only-testing:AIChatTests`로는 72/72 통과). 판정 순서: **먼저 `-only-testing:<단위 타깃>`으로 격리 실행해 진짜 실패인지 부하 플레이크인지 가른다.** 애초에 안 깨지게 쓰려면 고정 `sleep` 대신 조건 폴링(원하는 상태가 될 때까지 짧게 재시도)으로 작성한다. 취소 전파처럼 대기 상한이 필요한 경우엔 상한을 넉넉히 잡는다 — 성공 시엔 즉시 반환이라 상한을 키우는 비용이 0이다.
- **고정 `sleep`을 조건 폴링으로 바꿀 때, 그 조건이 시작 시점에 반드시 거짓인지 확인한다.** 아무것도 안 기다리는 조건을 쓰면 테스트가 통과하는 게 아니라 **검증을 건너뛴다**(실사례: `canSend || inputText.isEmpty`로 폴링했는데 `send()`가 이미 `inputText`를 비워 항상 참이었다). 폴링 직전에 그 조건이 거짓임을 `#expect`로 한 번 못 박아두면 이 실수가 드러난다.
- **"원소가 추가됐다"를 "그 원소의 내용이 다 찼다"의 신호로 쓰면 안 된다.** 스트리밍 말풍선은 빈 채로 먼저 생기므로 `waitUntil { messages.count == 3 }` 직후에 텍스트를 단언하면 경합한다 — 통과하던 테스트가 구현에 비동기 홉이 하나 늘었다는 이유만으로 깨진다(실사례: `TypewriterStream`을 두 Task로 가르자 실패). 내용을 볼 거면 `status == .completed`까지 폴링 조건에 넣는다.
- **검증하려고 상수를 임시로 바꿨으면, 소스를 원복한 뒤 반드시 재빌드·재설치까지 해야 한다.** 소스만 되돌리고 끝내면 시뮬레이터에는 임시값 빌드가 남아 있어, 이후 그 화면을 보는 사람에게는 바뀐 동작이 그대로 보인다(실사례: 스트리밍 속도를 20ms→250ms로 올려 중간 상태를 캡처한 뒤 소스만 원복해, 사용자가 12.5배 느린 앱을 보고 이상을 지적했다). `git diff`가 깨끗한 것은 **소스가 원복됐다는 증거일 뿐 시뮬레이터 상태와는 무관하다** — 원복 확인을 diff로만 끝내지 말 것.
- **`build_sim`은 테스트 타깃을 컴파일하지 않는다** — 테스트 코드를 고친 뒤 `build_sim`이 `SUCCEEDED`라고 해서 통과한 게 아니다(실사례: 테스트 헬퍼 접근 제어 실수로 `test_sim`에서 컴파일 에러 10개가 났는데 `build_sim`은 깨끗했다). 테스트 파일을 건드렸으면 판정은 반드시 `test_sim`으로 한다.
- **임시 코드를 문자열 매칭으로 원복하지 않는다** — 저장 훅의 SwiftFormat이 넣어둔 `//` 주석을 `///`로 바꿔 매칭이 빗나간다. 스크립트로 되돌릴 거면 `assert`로 대상 존재를 못 박아 조용히 실패하지 않게 하고(빗나가면 즉시 드러난다), 그냥 `git checkout -- <파일>`이 가장 안전하다.
- **호출부를 정규식으로 일괄 치환하면 선언부까지 같이 바뀐다** — `(?<![.\w])layoutText\b → message.layoutText` 같은 패턴은 확장의 `var layoutText: String {` 선언에도 걸려 `var message.layoutText: String {`를 만든다(실측, 컴파일 불가). 치환 후 결과 줄 수만 세지 말고 **선언부가 온전한지 `grep`으로 눈으로 확인**한다. 치환 스크립트에는 기대 건수 `assert`를 넣되, 부분 문자열이 서로 포함 관계면(`text: x,`가 `text: x, font:`에 포함) 건수 가정이 먼저 깨지므로 실제 건수를 세어 보고 짠다.
- **검증용 `grep`이 0건을 반환하면 결론을 내리기 전에 도구 문법부터 의심한다** — 훅이 `grep`을 `rtk grep`으로 재작성하는데 Rust 정규식이라 BRE의 `\|` 교체가 안 먹는다(실사례: `"A\|B"` 패턴이 실재하는 2건을 0건으로 보고해, 코드 리뷰 지적을 잘못된 인용으로 기각할 뻔했다). 교체가 필요하면 `grep -E`를 쓰거나 패턴을 나눠 각각 돌린다.
- 테스트 결과에 `DTDKRemoteDeviceConnection: Failed to start remote service ... "The device is passcode protected"` 스택트레이스가 무더기로 찍히는 건 **연결된 실기기를 xcodebuild가 훑는 노이즈**로, 시뮬레이터 테스트 결과와 무관하다. MCP 태스크가 이 때문에 `failed`로 보고될 수 있으니 실제 통과/실패는 `testCases` 배열이나 로그의 `Test case ... passed/failed` 줄로 판단한다.

## 텍스트 조판 · 줄 수 · 말줄임

- 말풍선 밀도 우선 줄바꿈은 **`UILabel` + `lineBreakMode = .byCharWrapping`** (`BubblePlainTextLabel`)로 연다. 저장·표시 문자열은 원문 `Message.text`다. 예전 ZWSP(`U+200B`) 삽입 경로는 제거됐다.
- **표시 문자열을 속여 줄바꿈을 여는 우회(ZWSP 등)를 “유지 + 회귀 테스트만”으로 닫지 않는다.** 복사·검색·a11y·UITest 이중 매칭 세금이 기능마다 다시 붙는다. 목표가 밀도 우선이면 먼저 **엔진 옵션(UILabel char wrapping)으로 우회를 제거**할 수 있는지 보고, 테스트-only 봉인은 그 다음이다.
- **렌더 엔진/문자열 모드와 접힘 측정을 한 커밋·한 PR 안에서 같이 맞춘다.** 렌더만 UILabel+원문이고 측정이 옛 모드(또는 ZWSP 문자열)인 **하이브리드를 중간 상태로 남기지 않는다** — 접힘 여부·분할 위치가 화면과 어긋나는 전형 경로다. 옛 변환 유틸(`MessageTextBreaking` 등)은 호출부 0 확인 후 **삭제**해 되돌리기 어렵게 한다.
- 말풍선에 `.frame(maxWidth:)`만 걸면 `HStack`+`Spacer` 앵커링에서 **짧은 글도 상한 폭까지 늘어난다**. 카카오톡식 hug는 `boundingRect`(max 폭 제약, **char wrapping paragraph** attributes)로 `min(콘텐츠 폭, maxWidth)`를 재 **`frame(width:)`로 고정**한다. hug를 `.fixedSize(horizontal: true)`로 흉내 내면 장문이 한 줄 ideal 폭으로 잡혀 잘리거나 줄바꿈이 깨지므로 쓰지 않는다.
- 말풍선 최대 폭·접힘 판정·표시 줄바꿈은 **같은 원문**과 **같은 유효 폭·같은 `lineBreakMode`** 를 써야 한다. `MessageLineLimit`은 CoreText + `byCharWrapping` paragraph로 줄을 세고, 렌더 UILabel도 동일 모드다. 폭 상한은 부모 `GeometryReader`에서 한 번 계산해 발신자 공통으로 내리고, 발신자별로 maxWidth를 다르게 주면 `Spacer` 정렬이 깨진다(위 `HStack` 규칙과 동일).
- 텍스트 줄 수를 `NSString.boundingRect` 높이 ÷ `font.lineHeight`로 세지 않는다. `CTFramesetterCreateFrame` + `CTFrameGetLines`로 조판 결과를 그대로 세고, `CTLineGetStringRange`가 각 줄의 끝 인덱스를 주므로 "N줄까지 자르기"에서 이진 탐색이 필요 없다. 측정 paragraph의 `lineBreakMode`를 렌더와 다르게 두면 접힘 경계가 어긋난다. **계약 잠금:** 공백 없는 영문 장문이 좁은 폭에서 `lineCount > 1`이어야 한다 — `byCharWrapping`을 빼면 이 단위 테스트가 깨진다 (`MessageLineLimitTests`).
- 접힌 말풍선을 `UIViewRepresentable`로 옮길 때 **「더 보기」 Button까지 한 UILabel에 넣지 않는다.** 텍스트 조각만 UILabel, 버튼은 SwiftUI 유지가 a11y 분리·`moreButton` id·예약 폭 계약을 덜 흔든다 (`CollapsedBubbleText`).
- `UILabel`/`UIViewRepresentable` 본문은 **`accessibilityLabel`에 원문을 명시**한다. attributedText만 두면 XCUITest `staticTexts[원문]`이 개행 포함 장문에서 실패할 수 있다. 트리가 개행을 공백으로 정규화하면 `label == 원문 OR label == 개행→공백`만 허용한다 (`UITestSupport`, Expand UITest).
- `truncationMode(.tail)`이 붙이는 말줄임표(U+2026)의 글꼴은 **잘린 지점 런의 글꼴**을 물려받는다 — 한글 한가운데서 잘리면 Apple SD Gothic Neo가 되고, 이 글꼴의 `…`는 CJK 관례대로 가운데 점(⋯)이라 같은 화면에서도 잘린 위치에 따라 모양이 달라진다(U+2026 글리프 y: SF −0.08 / SD Gothic Neo +5.68). 모양을 고정해야 하면 렌더러에 맡기지 말고 문자열에 직접 `…`를 붙인다 — 문자열 안의 `…`는 글리프 커버리지 기준으로 SF에 배정돼 한글 바로 뒤에서도 항상 베이스라인이다.
- **attributed 경로에서 문자열에 직접 붙인 `…`도 글꼴만 주고 전경색을 빼면 안 된다.** `BubblePlainTextLabel(attributedText:)`는 런 색에만 의존하고 `UILabel.textColor`를 안 맞춘다. 색 없는 글리프는 기본 `.label`로 떨어져 **사용자 말풍선(흰 글자) 접힘 마지막 줄에서 말줄임만 검게** 보인다. 글꼴은 시스템(CJK 가운데 점 방지), **색은 head/본문 런의 `foregroundColor`를 상속**한다 (`MessageLineLimit.lastLineText`).
- **AI 응답 인라인 마크다운은 표시만 바꾸지 말고 측정·렌더가 같은 attributed를 쓴다.** plain CoreText 줄 수에 bold 런 폭이 안 들어가면 접힘·말줄임이 어긋난다. 변수 `String`을 `Text`/`LocalizedStringKey`로 넘기지 않는다 — 마크다운이 안 파싱되거나 `%`가 포맷으로 깨진다. 표준 경로는 `AttributedString(markdown:)` → `NSAttributedString` (`MessageInlineMarkdown`). **스트리밍 틱마다 재파싱하지 않는다** — 미완성 `**`/`~~` 깜빡임·CPU 폭발. 스트리밍 plain 유지, `.completed`에서 1회 파싱.
- **한글 body 폰트에 italic face/slant trait를 얹어도 화면에 기울임이 거의 안 보인다.** `UIFontDescriptor` slant나 `traitItalic`은 영문 이탤릭 face가 있을 때만 유효하고, Apple SD Gothic Neo 계열은 italic face가 없다. 이탤릭은 **`.obliqueness`(합성 기울기)** 를 런에 넣는다 — UILabel/CoreText가 글리프를 기울여 그린다.
- `Text`의 `.lineSpacing`은 시각 높이만 바꾸고 조판 줄 수에는 들어가지 않는다 — 줄 수 판정에 행간 보정항을 넣지 않는다(넣으면 접힘 판정이 틀어진다). UILabel 경로의 행간은 paragraph `lineSpacing`으로 넣고, **측정 attributes에는 행간을 넣지 않는다**. 세로 잘림 방어용 `.fixedSize(horizontal: false, vertical: true)`는 가로를 `true`로 두면 maxWidth 줄바꿈이 무력화되므로 가로는 false로 유지하고, 접기(`lineLimit`)를 함께 써도 걷어낼 필요 없다.
- **글자마다 자라는 라벨에 전체 문자열을 다시 주면 조판·드로우가 통째로 다시 돈다 — 누적 O(n²).** 라벨 하나로 스트리밍을 그리면 틱당 비용이 **전체 길이에 비례**한다(실측 2500자: `sizeThatFits` 2.9ms + `drawText` 1.6ms, 스트리밍 중 시뮬레이터 CPU 코어 하나의 47%. 실기기는 2~3배라 QA가 본 100~128%와 맞는다). 증상은 "길어질수록 점점 느려짐"이고, 이건 **무엇이 무거운가가 아니라 매 틱 전체를 훑는 작업이 있는가**의 문제다. 해법은 **확정 구간을 불변 라벨로 얼리고 마지막 tail만 갱신**하는 것(`StreamingBubbleText` + `MessageLineLimit.settledSplit`) — 틱당 비용이 tail 길이로 묶여 누적이 O(n)이 된다. 틱 병합(flush 주기화)은 횟수만 줄여 **차수를 못 바꾸고**, "1글자씩 일정한 속도" 요구와도 충돌한다.
  - 블록 경계는 반드시 **CoreText 줄 시작**이어야 한다. 글자 단위 줄바꿈은 greedy라 줄 시작만 같으면 이후 경계가 그대로 재현된다(실측: 한글·영문·개행·공백없음 4종에서 단일 라벨과 줄 수 완전 일치).
  - 블록 끝에 **개행이 남으면 라벨이 빈 줄을 하나 더 그린다**(실측 +23pt). 블록 경계 자체가 줄을 끝내므로 떼어낸다.
  - 라벨을 쌓으면 각 intrinsic height에 `ceil`이 따로 걸려 **높이 오차가 블록 수에 비례해 누적**된다(400자 블록 6~7개 = 2~5pt, 200자 12~15개 = 4~11pt). 블록을 작게 잡을수록 틱당 비용은 싸지고 오차는 커진다.
- 줄바꿈 정본이 바뀌면 **관련 Task 이슈·에픽 표·QA 파일 맵을 같은 문서 패스에서 고친다** (예: ZWSP 회귀 → UILabel 단일화, 접근성 이슈의 “본문은 원문 라벨” 전제, 에픽 표 행). 스펙만 바꾸고 이슈 본문이 옛 수단을 가리키면 다음 워크트리가 폐기된 경로를 구현한다.
- **옛 조사 절(「조사 B」 등)의 파이프라인 다이어그램을 후속 스펙에 복붙하지 않는다.** 조사 B는 ZWSP·`Text(verbatim:)`를 적었지만 UILabel 단일화 이후 정본은 UILabel 원문이다. 후속 Task 스펙을 쓸 때는 조사 문서가 아니라 **현재 소스·최신 정본 스펙**으로 파이프라인을 다시 고정한다. 조사는 리스크 목록으로만 쓰고 경로 정본으로 쓰지 않는다.
- **파서·측정 단위 테스트만으로 “AI+completed에만 적용” 뷰 가드를 잠글 수 없다.** `MessageBubble` 게이트를 지워도 단위 스위트는 통과한다. 가드를 단위로 잠그려면 `nonisolated` pure 헬퍼로 뽑거나, UI/시뮬 검증으로 보완한다 — “파서 테스트 통과 = 배선 완료”로 단정하지 않는다.

## 빌드 캐시 · SourceKit 진단

- incremental build(xcodemake)가 실패하면 `session_set_defaults({ preferXcodebuild: true })`로 전환 후 재시도. 실패뿐 아니라 "`SUCCEEDED`인데 durationMs가 비정상적으로 짧고(수십 ms) 방금 추가한 새 타입에 대해 SourceKit이 'Cannot find type in scope'를 띄우는" 경우도 같은 증상이다 — 실제로는 증분 캐시가 새 파일을 못 보고 있는 건데 build 결과만 보면 성공처럼 보이니 속지 말 것. xcodemake가 생성하는 `AIChat/Makefile`, `AIChat/xcodemake_*.log`는 `.gitignore`에 이미 등록돼 있다(커밋 대상 아님).
- `preferXcodebuild: true`로 전환해 정상 소요시간(수백 ms~수 초)의 `SUCCEEDED` 빌드를 받은 뒤에도, `Write`/`Edit` 직후 시스템이 "Cannot find type in scope" 같은 SourceKit 진단을 새 타입에 대해 보여줄 수 있다 — 이건 위 캐시 버그와 별개로, 에디터의 SourceKit 인덱스가 방금 추가된 파일을 아직 못 따라잡은 것뿐인 흔한 지연이다. 판단 기준은 진단 메시지가 아니라 실제 `build_sim`/`test_sim` 결과(`errors: []`, 합리적인 durationMs)다 — 그 결과가 깨끗하면 진단은 무시하고 진행한다. 같은 지연이 새로 추가한 `import` 구문(예: `import UIKit`, 새 테스트 파일의 `@testable import AIChat`)에 대한 "No such module 'X'" 형태로도 나타난다 — 증상만 다를 뿐 원인과 판단 기준은 동일하다.
- **빌드/테스트가 `unable to write manifest to ... .xcbuilddata/manifest.json ... "No space left on device"`로 죽으면 코드 문제가 아니라 디스크 문제다.** 이 머신은 워크트리 세션마다 `~/Library/Developer/XcodeBuildMCP/workspaces/<워크트리>-<해시>/`에 DerivedData를 따로 만들어(각 200MB~1GB) 금방 찬다. 확인은 `df -h /`가 아니라 **`df -h /System/Volumes/Data`**로 한다 — `/`는 읽기 전용 시스템 볼륨이라 원래 여유가 수백 MB뿐이고, 그걸 보고 "디스크가 찼다/안 찼다"를 판단하면 둘 다 틀린다(실제로 `/`의 135Mi를 근거로 오진했다). `du -sh ~/Library/Developer/XcodeBuildMCP/workspaces/*`로 **지금 워크트리가 아닌** 것들을 먼저 후보에 올린다(전부 재생성 가능). `result-bundles`(xcresult 리포트)가 `test-products`보다 지우기 안전하다. `~/Library/Developer/Xcode/iOS DeviceSupport`도 GB 단위지만 실기기 재연결 시 재다운로드가 필요하다. **삭제는 사용자 확인을 받는다** — 다른 워크트리 세션이 그 캐시를 쓰는 중일 수 있고, 실제로 `rm -rf`가 권한 거부된 사례가 있다(그때는 `! <명령>` 형태로 넘긴다).
  - **`test_sim`이 `Unable to Install "AIChat" … isn't enough storage` / `XCTestDevices/... No space left on device`로 죽어도 같은 계열이다.** 단위 테스트 러너 클론이 `~/Library/Developer/XCTestDevices/`에 쌓이며(실측 수십~100GB+) Data 볼륨을 먼저 채운다. `du -sh ~/Library/Developer/XCTestDevices`로 크기를 보고, 클론 디렉터리 정리는 재생성 가능하니 후보에 올린다(역시 사용자 확인 후). DerivedData만 지우고 XCTestDevices를 안 보면 같은 에러가 반복된다.
  - **완전히 차면 Bash 도구 자체가 죽는다** — 모든 호출이 출력 파일을 디스크에 쓰므로 `df`·`du`·`rm` 같은 정리 명령마저 `ENOSPC ... open '.../tasks/*.output'`으로 실패한다. `! <명령>`도 같은 경로를 타서 소용없다. 이 상태가 되면 **Claude Code 밖의 터미널 창**에서 지우게 안내하는 것 외에 방법이 없으니, 그 전에(수백 MB 남았을 때) 정리한다.

## 시뮬레이터 자동화

- **`type_text`로 넣는 텍스트가 깨진다 — 해결됨. 항상 `type_text` 대신 페이스트보드로 넣는다.**
  **"나는 영문만 입력하니 상관없다"는 착각하지 말 것** — 이 버그는 입력하는 텍스트의 언어가 아니라 **그 순간 호스트 macOS의 활성 입력기 상태**에 좌우된다. 호스트 입력기가 한글 2벌식이면 완전한 영문 문자열("Message one alpha bravo...")도 `ㅁㄴㅊㅑ ㅗㅜㅕ ㄸㅃㅏㅁㅗ...`처럼 통째로 깨진다(실측: 순수 영문 테스트 문구로 재현). 그래서 "지금 입력할 텍스트가 한글인지"로 판단하지 말고, 시뮬레이터에 텍스트를 넣을 일이 있으면 **매번 기본값으로** 아래 페이스트보드 경로를 쓴다:
  ```
  printf '%s' '<넣을 텍스트>' | xcrun simctl pbcopy <UDID>
  long_press(필드 elementRef, 1200)      # 단축바에 "Paste"가 뜬다
  touch(Paste의 elementRef, down+up)     # "Paste"는 text role이라 tap 대상이 아님 → touch로 누른다
  ```
  실측으로 한글+영문 혼용 장문이 깨짐 없이 그대로 들어갔다. 이 경로는 IME를 안 거치므로 `type_text`의 자모 깨짐·composing 꼬임 문제가 원천적으로 없다. 단축바가 안 보이면 필드를 먼저 `touch`해 입력 세션을 띄운 뒤 `long_press`한다.
- **`simctl pbcopy`로 넣은 내용이 실제로 붙여넣기될 때는 다른 텍스트로 바뀌어 있을 수 있다** — `pbcopy` 직후 `pbpaste`로 확인해도 그 사이 뭔가(다른 프로세스·세션 등, 정확한 출처는 미확인) 시뮬레이터 페이스트보드를 다시 덮어쓸 수 있다(실측: 방금 복사한 문자열 대신 무관한 텍스트가 붙여넣어짐, 여러 번 재현). 스크롤·전송 재현처럼 **붙여넣는 내용 자체가 중요하지 않은 테스트**는 무시하고 진행해도 되지만, 내용이 검증에 중요하면 `long_press`→`touch(Paste)` 직전에 `pbcopy`를 다시 실행해 텀을 최소화하고, 붙여넣힌 뒤 `snapshot_ui`의 필드 `value`로 실제 들어간 텍스트를 확인한다.
- 위 페이스트 흐름에서 `long_press`가 "Paste" 콜아웃을 안 띄우는 경우가 있는데, 필드에 **이미 텍스트가 들어있으면** 재현된다 — 기존 텍스트가 있는 지점을 `long_press`하면 콜아웃 대신 커서 배치(돋보기) 모드로 들어가는 것으로 보인다. 필드가 **비어 있을 때** `long_press`하면 안정적으로 "Paste"가 뜬다. 이미 텍스트가 있는 필드를 다시 채워야 하면(예: 이전 시도가 깨진 문자열을 남긴 경우) 재시도를 늘리기보다 앱을 재실행(`stop_app_sim` → `launch_app_sim`)해 필드를 비운 뒤 다시 시도한다.
- `type_text`가 한글로 깨지는 **원인은 "AXe가 US 문자만 지원"이 아니다** — 시뮬레이터 메뉴 `I/O ▸ Keyboard ▸ Use the Same Keyboard Language as macOS`가 기본 켜져 있어 **호스트 macOS의 입력기를 그대로 미러링**하기 때문이다. macOS 입력기가 한글 2벌식이면 AXe가 보낸 US 스캔코드가 한글 IME로 해석돼 `ascii check` → `ㅁㄴ챠ㅑ 촏차`가 된다. 호스트 입력기를 ABC로 바꾸거나 저 메뉴를 끄면 `type_text`도 정상 동작하지만, **호스트 설정을 건드리지 않는 위 페이스트보드 경로를 기본으로 쓴다.**
- `snapshot_ui` 등 ui-automation 도구가 `No translation object returned for simulator` 에러를 내면 앱/설정 문제가 아니라 호스트의 `CoreSimulatorBridge`가 멈춘 경우가 많다 — `pgrep -f "/usr/libexec/CoreSimulatorBridge" | xargs kill -9`로 재시작(launchd가 자동 재기동)하면 대부분 즉시 해결됨. 이 증상은 `list_sims`가 모든 시뮬레이터를 `Shutdown`으로 보고하는 형태로도 나타난다(참고: getsentry/XcodeBuildMCP#458). 같은 근본 원인이 `install_app_sim`/`build_run_sim`이 `Mach error -308 (ipc/mig) server died`로 실패하는 형태로도 나타나는데, 이 경우는 kill 없이 그냥 한 번 더 시도하는 것만으로도 대부분 해결된다.
- `swipe`의 시작 좌표가 네비게이션 바 경계 근처(예: y≈115, 상단 세이프에어리어 바로 아래)면 스크롤 제스처가 조용히 무시된다 — 도구는 성공을 반환하지만 이후 `snapshot_ui`의 `screenHash`가 전혀 안 바뀐다. 시작점을 콘텐츠 영역 안쪽(예: y≈249)으로 옮기면 정상 동작한다. "스크롤이 안 먹는 것 같다"고 콘텐츠 양을 계속 늘리기 전에 시작 좌표부터 의심한다.
- `tap`(접근성 activate)과 `touch`(HID 터치)는 결과가 다르다. `snapshot_ui`의 `text` role 요소(단축바의 `Paste` 등)는 tap 타깃 목록에 없어 `tap`으로 못 누르지만 `touch`로는 눌린다. 입력 세션(단축바)도 `touch` 쪽에서 더 잘 뜬다 — 탭이 안 먹는 것 같으면 `touch`로 한 번 더 시도한다.
- `TextField(axis: .vertical)` 같은 멀티라인 자동 확장을 테스트할 때 `key_press`로 Return을 눌러 줄바꿈을 넣으려 하면 반영되지 않을 수 있다 — 필드 너비를 넘는 긴 한 문장(자동 줄바꿈)을 넣거나, 개행이 포함된 문자열을 페이스트보드로 붙여넣는다.
- `type_text`로 텍스트를 넣고 곧바로 전송 버튼을 탭했는데 아무 반응이 없는 게 반복되면, 같은 세션에서 재시도를 늘리기보다 앱을 완전히 재실행(`build_run_sim`)하는 쪽이 빠르다 — IME composing 상태가 누적돼 접근성 레이어엔 값이 찍히지만 SwiftUI 바인딩엔 커밋되지 않는 상태로 꼬이는 경우가 있다(페이스트보드 경로를 쓰면 이 증상 자체가 안 생긴다).
- **포커스는 시각 검증된다** — 필드를 `touch`하면 캐럿이 스크린샷에 찍히고, 입력 세션이 살아 있으면 단축바(`AutoFill`/`Paste`)가 함께 보인다. `wait_for_ui`의 `focused` predicate는 텍스트필드 role에 지원되지 않으므로(`TARGET_NOT_ACTIONABLE`) 캐럿·단축바를 근거로 판단한다.
- **미해결: 소프트웨어 키보드 자체는 화면에 렌더링되지 않는다.** 다음을 모두 시도했지만 안 떴다 — 실제 HID `touch`로 포커스, `~/Library/Preferences/com.apple.iphonesimulator.plist`의 `DevicePreferences.<UDID>.ConnectHardwareKeyboard = false`(시뮬레이터 메뉴에서 해제 확인됨), 기기 완전 재부팅, `open_sim`으로 Simulator.app UI 부착. 접근성 트리에도 `keyboard-key` role이 없다. 키보드 높이에 반응하는 레이아웃(입력창 밀림 등)을 검증해야 하면 사용자에게 시뮬레이터에서 직접 확인을 요청한다.

- **부팅해 쓰던 기기가 세션 도중 `Shutdown`으로 돌아가 있을 수 있다** — `simctl` 명령이 갑자기 `Unable to lookup in current state: Shutdown`(code 405)으로 무더기 실패하면 앱이나 도구가 깨진 게 아니라 기기가 잠든 것이다. `xcrun simctl bootstatus <UDID> -b`로 부팅을 보장한 뒤 그대로 재시도하면 된다(실제로 한 세션에서 두 번 겪었다). 오래 걸리는 빌드·대기 사이에 잘 일어나므로, 실패를 원인 조사로 확대하기 전에 상태부터 확인한다. **디스크 여유가 한 자릿수 GB로 낮을 때 이 재부팅이 반복적으로(한 세션에 여러 번) 일어나는 경우를 실측했다** — `screenshot`이 `No space left on device`로 실패하는 것과 같은 시점에 함께 나타났다. 반복되면 재부팅만 계속하지 말고 `df -h /System/Volumes/Data`부터 확인한다(「빌드 캐시 · SourceKit 진단」의 디스크 정리 절차 참고).

## 화면 검증 (스크린샷 · 런타임 값)

- `screenshot`이 반환하는 이미지는 압축된 저해상도(예: 368×800)라 5~10pt 수준의 디테일(말풍선 꼬리 이음새, 모서리 radius 차이 등)은 전체 스크린샷을 한 번 보는 것만으로 "확인됐다"고 판단하면 안 된다 — 실제로 이렇게 판단했다가 나중에 정렬/이음새 버그를 놓친 적 있음. `returnFormat: "path"`로 원본 파일을 받은 뒤 `sips -c <h> <w> --cropOffset <top> <left> in --out crop.jpg && sips -z <h> <w> crop.jpg --out zoom.png`로 문제 영역만 잘라 확대하고 `Read`로 다시 봐야 픽셀 단위 판단이 가능하다. 확대해도 "균일한가"(행간, 정렬 간격 등)는 눈으로 갈리므로, 그럴 땐 `NSBitmapImageRep.colorAt`으로 행별 어두운 픽셀 수를 세는 짧은 AppKit 스크립트를 스크래치패드에 두고 밴드 위치를 수치로 뽑는다.
- 다크모드 확인은 XcodeBuildMCP에 전용 도구가 없다 — `xcrun simctl ui <시뮬레이터UDID> appearance dark|light`로 전환 후 `screenshot`으로 확인한다. Dynamic Type도 마찬가지로 `xcrun simctl ui <UDID> content_size accessibility-extra-extra-extra-large`(복귀는 `large`)로 바꾼다. **둘 다 부팅된 기기에서만 먹는다** — `Shutdown` 상태면 `Unable to lookup in current state: Shutdown`(code 405)이 나므로 `boot_sim`부터 하고, 설정은 앱 실행 **전에** 바꿔둔다. 복귀(`large`/`light`)도 잊지 말 것 — 시뮬레이터 설정은 소스 원복과 무관하게 남는다.
- **Reduce Motion On 강제:** `xcrun simctl spawn <UDID> defaults write com.apple.Accessibility ReduceMotionEnabled -bool true` 후 앱 **재실행**. 확인: `defaults read … ReduceMotionEnabled` → `1`. 끝나면 `false`로 되돌린다(다크/Dynamic Type과 같이 시뮬에 남는다). `#Preview` 주입으로 대체하지 말 것(「SwiftUI 접근성」). 대기 인디케이터 같은 **짧은 과도 모션**은 `QA:slow`여도 TTFT 윈도우가 짧아 자동화 스크린샷이 완료 화면만 잡기 쉽다 — 모션 DoD는 수동 On/Off가 본편이고, 전용 UITest를 억지로 늘리지 않는다.
- `build_run_sim`이 반환하는 `osLogPath`는 `subsystem == "<bundleId>"`로 필터링된 OSLog 스트림이라, 평범한 Swift `print()`는 이 subsystem 태그가 없어 잡히지 않는다 — 아직 어떤 UI도 소비하지 않는 로직을 임시로 검증하려고 `print()`를 넣어도 이 로그 파일에서는 확인 불가능하다. 억지로 방법을 찾기보다 "이 값을 실제로 그리는 다음 작업에서 처음 검증 가능하다"고 솔직하게 남기고 넘어간다. 반대로 **이미 화면에 그려지는 값의 원인을 추적할 때는** `os.Logger(subsystem: bundleId, category:)`로 임시 계측하는 게 가장 빠르다 — 레이아웃 계산값(폭·줄 수 등)이 예상과 다를 때 스크린샷에서 역산하지 말고 `Logger(...).debug()`로 찍은 뒤 `osLogPath`를 grep한다. 콜백이 짧은 시간 안에 여러 번 불려 애니메이션과 충돌하는지(예: 값이 잠깐 반전됐다 돌아오는 깜빡임) 확인해야 하면 `print("...\(Date().timeIntervalSince1970)...")`처럼 타임스탬프를 같이 찍어 호출 간격(ms)까지 비교한다 — 실측으로 밀리초 단위 경합을 확인해야 "애니메이션 진행 중에 반전된다"를 추측이 아니라 근거로 말할 수 있다. 검증이 끝나면 계측 코드는 지운다.
- **`build_run_sim`이 여는 `osLogPath` 캡처는 앱 런치보다 몇 초 늦게 시작한다** — 런치 직후 한 번만 찍는 로그(시작 시 계산·검증 루틴 등)는 그 파일에 안 남아 "로그가 0건"으로 보인다(실측: launch 18:07:02 / 캡처 시작 18:07:08). 파일이 이미 열려 있는 상태에서 `xcrun simctl terminate` → `launch`로 앱만 다시 띄우면 같은 파일에 잡힌다. 계측이 안 나올 때 코드부터 의심하기 전에 이 타이밍을 먼저 본다.
- **몇 초 만에 지나가는 과도 상태(스트리밍 중 텍스트, 짧은 애니메이션)는 스크린샷 타이밍으로 못 잡는다 — 그 속도를 지배하는 상수를 임시로 크게 올린다.** `tap`/`touch`/`snapshot_ui` 호출 자체가 2.5초 이상 걸려서(UI가 계속 변하는 동안엔 `runtime snapshot did not settle within 2500ms`로 실패한다) 지연을 아무리 조절해도 완료 후 화면만 잡힌다 — 실제로 4번 시도해 전부 실패했다. 지연 상수를 12배로 올리면(예: 글자당 20ms → 250ms) 첫 시도에 잡힌다. 테스트용으로 주입 가능하게 만들어 둔 값이면 같은 코드 경로를 그대로 검증하는 셈이다. **확인 후 원복은 재빌드·재설치까지**(「테스트 실행 · 플레이크」 참고).
  - 덧붙여 `snapshot did not settle within 2500ms` 경고 자체가 "UI가 계속 바뀌는 중"이라는 **간접 증거**다 — 정지 화면을 못 잡았더라도 이 경고로 "동작은 하고 있다"까지는 말할 수 있다.
- 조건부로 렌더링되는 오버레이(`if isAtBottom { ... }` 같은)를 다크모드·Dynamic Type에서 강제로 띄워 스타일만 확인하고 싶을 때, **그 판정에 쓰이는 상태값의 초기값만** 바꾸면(예: `@State var isAtBottom = false`) 안 통할 수 있다 — 실시간 판정 로직(`onPreferenceChange` 등)이 레이아웃이 안정되는 즉시 실측값으로 되돌려버리기 때문이다. 확실히 강제하려면 **`if` 조건 자체**를 임시로 `if true`로 바꿔 확인한 뒤 원복한다.

## 성능 회귀 · 자동 검증의 사각

- **이 프로젝트의 자동 검증(`build_sim`·`test_sim`·UITest·스크린샷)은 성능 회귀를 구조적으로 못 잡는다. "다 통과했다"를 성능 근거로 쓰지 않는다.** P0 성능 버그가 전 구간 그린인 상태로 휴먼 QA에 실기기에서 처음 걸렸고, 원인은 다음 다섯 가지가 겹친 것이다 — 하나만 고쳐도 안 되니 성능은 **별도 계측으로만** 말한다.
  - UITest는 `UITestingBootstrap`이 `characterDelay: .zero`·`chunkDelay: .zero`로 조립한다 — 타이핑 페이싱 경로를 **아예 안 탄다**.
  - `MockChatService`는 입력을 에코한다 — **사람이 장문을 붙여넣지 않으면 장문 스트림 자체가 생기지 않는다.** 자동 픽스처는 전부 짧다.
  - 비용이 O(n²)면 짧은 픽스처에서는 신호가 안 보인다. 2500자에서 터지는 것이 200자에서는 156배 작다.
  - `swipe` 자동화에는 "버벅였다"는 **판정 신호가 없다** — 스크롤 부드러움은 통과/실패로 안 나온다.
  - 시뮬레이터는 Mac CPU + 60Hz다. 실기기는 CPU가 2~3배 느리고 ProMotion 120Hz라 **프레임 예산이 절반(8.3ms)** 이다. 시뮬에서 코어 47%면 실기기에서는 100~140%가 된다(실측 대조: QA 스크린샷 99%·피크 128%).
- **"길어질수록 점점 느려진다"는 증상 자체가 O(n²) 시그니처다.** 무엇이 무거운가가 아니라 **매 틱 전체를 훑는 작업이 몇 개인가**로 본다. 항목별로 `n` 구간별 평균을 찍으면 상수인지 비례인지 한눈에 갈린다(실측 예: `sizeThatFits` 1,042→2,042→2,900µs = 비례 / `persist` 565µs 고정 = 상수). 이 표가 나오기 전에는 어떤 후보도 원인으로 단정하지 않는다.
- **`ps -o %cpu`는 프로세스 수명 전체의 누적 평균이라 구간 부하가 아니다.** 이걸로 스트리밍 CPU를 재면 시간이 갈수록 값이 떨어져 "부하가 끝났다"로 오독한다 — 실제로 이 오독으로 틀린 수치를 보고했다가 `sample`과 모순돼 철회했다. 구간 부하는 **`ps -o time=`(누적 CPU 시간)의 델타 ÷ 벽시계 구간**으로 잰다. Xcode CPU 게이지의 %는 1코어 기준이라 100% 초과 표기가 정상이며, 초과분은 렌더/CoreAnimation 스레드가 같이 타고 있다는 뜻이다.
- **성능 계측 하네스는 launch argument로 시나리오를 자동 재생하게 만든다.** 붙여넣기·탭에 의존하면 A/B를 반복할 수 없다(페이스트보드가 덮어써지는 문제도 겹친다 — 「시뮬레이터 자동화」). `-perf-long` 식으로 긴 입력을 미리 채우고 자동 `send()`까지 태우면 매 측정이 같은 조건이 된다. 하네스와 계측은 커밋 금지 주석을 달아 두고, 제거 후 **`grep`으로 잔존 0건을 확인한 뒤** 커밋한다.
- **A/B는 계측을 양쪽에 그대로 둔 채 같은 조건으로 잰다.** 수정 후에만 계측을 떼면 개선폭에 계측 오버헤드가 섞여 부풀려진다. 이번 14.18초 → 8.83초는 양쪽 다 probe를 붙인 채 잰 값이라 유효하다.
- **성능 이슈에는 "계측으로 배제한 후보"도 같이 적는다.** 원인만 적으면 다음 사람이 이미 아닌 것으로 확인된 경로(persist·Markdown 파싱·자동 스크롤 등)를 다시 판다. 앞의 P0 성능 이슈가 이 형식을 따랐다.

## 로컬 영속화 (UserDefaults · Codable)

- `UserDefaults`는 `Sendable`을 선언하지 않는다 — 내부적으로 스레드 안전하더라도, 이를 저장 프로퍼티로 갖는 구조체를 그냥 `Sendable`로 선언하면 "stored property ... has non-Sendable type 'UserDefaults'; this is an error in the Swift 6 language mode" 경고가 뜬다(`preferXcodebuild: true`로 받은 실제 빌드 결과에서 확인, SourceKit 진단이 아니라 빌드 경고임에 주의). `@unchecked Sendable`로 명시하고 왜 안전한지(불변 저장 프로퍼티 + Apple이 스레드 안전을 보장) 주석을 남긴다.
- **재시도 버튼을 "실패 유형이 재시도 가능"만으로 켜면 안 된다.** 유형 정책(`isRetryable`)과 재요청 원본 맵(`failedRequests`)은 다른 축이다. 원본이 없는 고아 `.failed`(맵 prune·유실·non-retryable 저장 규칙)에서도 유형만 보면 버튼이 살아 있고 `retry`는 no-op — 죽은 컨트롤이 된다. **버튼 노출은 맵 멤버십(`canRetry`)으로**, 유형은 문구·재시도 불가 안내 문구용으로만 쓴다.
- **`PersistedState`에 필드를 새로 추가할 때**는 키가 없는 옛 JSON이 통째로 디코딩 실패하지 않게 **옵셔널**로 둔다(`failedRequests` 실사례). 반면 **이미 저장 중인 타입에 옵셔널 프로퍼티를 추가**하는 경우(예: `Message.failure`)는 합성 `Codable`이 `decodeIfPresent`를 쓰므로 수동 `init(from:)` 없이도 키 누락 테스트가 통과할 수 있다. "옵셔널이면 무조건 수동 Codable"로 일반화하지 말고 **키 없는 JSON 디코드 테스트로 확인**한다.
- **진행 중 상태(스트리밍·대기 등)는 저장될 수 있고, 복원되면 그걸 이어받을 주체가 없어 영구히 고착된다.** 저장 트리거가 그 상태와 무관해 보여도(사용자 메시지 전송 등) 스냅샷에는 같이 실린다 — 실사례: 응답 대기 중 두 번째 전송이 `.pending` 빈 말풍선을 함께 저장했고, 재실행 시 그게 복원돼 대기 인디케이터가 영영 돌았다. **비종료 상태는 복원 시점에 정규화한다.** 재요청 원본 맵 도입 이후: 재요청 원본 맵이 있는 비종료는 `.failed`+재시도로 닫고, 맵 없는 고아만 텍스트→`.completed`/빈 폐기다. **정규화 결과를 디스크에 write-back하지 않으면** 매 콜드 스타트가 같은 정규화를 반복하고, 다른 프로세스가 옛 스냅샷을 읽을 수 있다 — restore 직후 `persist()`를 한 번 호출한다. 새로 상태를 하나 추가할 때 "이게 저장 경로에 실리면 복원 후 어떻게 보이나"를 반드시 확인할 것.
- **사용자 stop에서 `Task.cancel()` 직후의 미정착 상태를 먼저 저장하지 않는다.** cooperative cancellation이 actor로 돌아오기 전에 앱이 suspend/종료되면 active 원본과 `.pending`/`.streaming`이 디스크에 남아 다음 실행에서 실패·재시도로 부활한다. 현재 active run ID를 키로 부분 말풍선 완료·빈 말풍선 제거·원본 삭제를 MainActor에서 동기 정착한 뒤 stopped snapshot을 저장하고, 늦게 도착한 Task cleanup은 같은 키에 대해 idempotent하게 만든다.
- **부분 스트리밍 텍스트를 재실행 후에도 살리려면 `append` 경로에서 write-through persist가 필요하다.** `send`/`finish`만 저장하면 사용자 메시지만 남고 AI 부분 글자는 디스크에 없다 — 앱이 글자 사이에 죽으면 복구 모델이 있어도 본문이 비어 있다.
- **재요청 원본 맵의 in-flight 키를 “전역 한 칸”으로 두면 동시 `deliver`가 서로의 키를 훔친다.** `retry`는 의도적으로 `responseTask`를 취소하지 않고 병렬로 흐른다(Timeout 스위트 전제). 공유 `batchKey`에 `promote`/`clearOnSuccess`를 걸면 A 스트리밍 중 B 재시도가 A의 맵 엔트리를 재키하거나 성공 시 B 키를 지운다 — **화면 응답은 맞아 보여도** 디스크 맵이 깨져 다음 복원 재시도가 죽는다. send 앵커 claim + **deliver run 지역 runKey**로 격리하고, 동시 스트리밍 중 맵에 두 배치가 동시에 있는지 테스트로 고정한다.
- 완료 기준에 "재실행 후 상태 유지"가 있으면, 그 상태가 가리키는 대상(예: 메시지 ID)이 이미 안정적이거나 영속화돼 있는지부터 확인한다 — mock 서비스가 매 실행마다 새 ID(`UUID()` 기본값 등)를 발급하는 구조라면, 상태(`Set<UUID>` 등)만 저장해도 그 ID가 가리킬 대상 자체가 재생성되어 화면에서 검증할 방법이 없다. 이 경우 상태가 가리키는 데이터 자체도 함께 영속화해야 완료 기준을 실제로 확인할 수 있다.
- **펼침(`expandedMessageIDs`)은 영속된다 — 검증 중 "더 보기"를 한 번 탭하면 앱 재실행 후에도 그 메시지는 펼쳐진 채라 `moreButton`이 없다.** Dynamic Type 매트릭스·겹침 확인처럼 **접힌 상태**가 더 필요하면 (a) **새 장문을 전송**해 접힌 말풍선을 다시 만들거나, (b) 펼침 탭 검증을 접힘 레이아웃 검증 **뒤로** 둔다. "재실행하면 다시 접힐 것"으로 가정하지 말 것.
- SwiftData는 iOS 17 표준 프레임워크지만 `@Model` 매크로가 참조 타입(클래스)에만 적용된다 — 이 프로젝트는 값 타입을 우선하므로(CLAUDE.md 아키텍처), 기존 값 타입 모델을 영속화해야 하면 그 타입을 클래스로 바꾸기보다 `Codable` + `UserDefaults`(소규모 데이터) 를 먼저 검토한다. 관계형 조회가 필요 없는 배열/집합 정도의 데이터에는 `ModelContainer` 설정이 과한 보일러플레이트다.
- 실제 "앱 재실행"을 시뮬레이터로 재현하려면 `build_run_sim`(재빌드 포함)이 아니라 `stop_app_sim` → `launch_app_sim`으로 프로세스만 재시작한다 — 재빌드는 매번 필요하지 않고, 프로세스만 재시작하는 쪽이 실제 사용자의 "앱 재실행"에 더 가깝다.
- "최초 실행(저장된 데이터 없음)" 상태를 재현하려면 XcodeBuildMCP에 전용 uninstall 도구가 없다 — `xcrun simctl uninstall <UDID> <bundleId>`(Bash)로 앱과 데이터 컨테이너를 지운 뒤 `install_app_sim` → `launch_app_sim`으로 재설치하면 된다.
  - **앱이 실행 중이면 이 uninstall이 실패하는데, 화면상으론 "깨끗한 첫 실행"과 구분되지 않는다** — 데이터가 남은 채 재설치돼 이전 대화가 복원되고, 그러면 신규 스트리밍 경로가 아예 안 타서 검증하려던 동작이 발생하지 않는다(실사례: timeout이 안 걸려 배선이 잘못된 줄 알았는데 실은 저장된 인사말이 복원된 것이었다). `xcrun simctl terminate`를 **먼저** 부르고, `2>/dev/null`로 에러를 숨기지 말 것. 의심되면 저장 시각을 확인한다 — Apple epoch 기준이라 `datetime(2001,1,1) + timedelta(seconds=...)`로 환산하면 이번 실행 전인지 바로 드러난다.

## MCP 설정

- `.mcp.json`의 env var(예: `XCODEBUILDMCP_ENABLED_WORKFLOWS`)를 바꿔도 새 도구가 안 잡힐 수 있다 — Claude Code가 `~/.claude.json`의 `projects.<경로>.mcpServers.<서버명>.env`에 MCP 서버 설정을 프로젝트별로 캐시해두기 때문에, `/mcp` 재연결은 물론 Claude Code 프로세스 재시작으로도 이 캐시는 갱신되지 않는다 — `~/.claude.json`의 해당 값을 `.mcp.json`과 동일하게 직접 고친 뒤 `/mcp` 재연결해야 반영된다.

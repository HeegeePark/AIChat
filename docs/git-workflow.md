# Git 워크플로우

## 브랜치 네이밍
- `feature/<에픽번호>-<간단설명>` — 에픽 하위 기능 개발
- `fix/<설명>` — 버그 수정
- `docs/<설명>` — 문서 작업

## 커밋 컨벤션
제목 줄은 [Conventional Commits](https://www.conventionalcommits.org/) 타입 접두사 + 한국어 설명, 본문은 `[변경 내용]`/`[영향 범위]` 블록으로 작성한다.

- `feat:` 새로운 기능
- `fix:` 버그 수정
- `refactor:` 리팩토링 (기능 변화 없음)
- `docs:` 문서 변경
- `chore:` 빌드/설정 등 잡무
- `test:` 테스트 추가/수정

예시:
```
feat: 카카오 로그인 연동

[변경 내용]
- 카카오 로그인 버튼 추가
- 토큰 갱신 로직 구현

[영향 범위]
- LoginViewController
- AuthManager
```

## PR 제목 컨벤션
커밋 제목 줄과 동일한 형식: 타입 접두사 + 한국어 설명 (예: `feat: 카카오 로그인 연동`).

## 작업 흐름
0. Superpowers 워크트리(`.superset/worktrees/AIChat/<자동생성이름>`)에서 세션을 시작하면 현재 브랜치명이 `feature/*` 컨벤션이 아닌 워크트리 자동 생성 이름(예: `literate-warlock`)인 경우가 있다. 코드를 건드리기 전에 `git branch --show-current`와 `git log --oneline origin/main..HEAD`로 그 브랜치가 `origin/main`과 같은 커밋인지 확인하고, 같다면 그 위에서 바로 `feature/<에픽번호>-<설명>` 브랜치를 새로 만들어 작업한다(사용자 확인 후).
1. 에픽 이슈 생성 (Epic 템플릿)
2. 에픽 하위 작업은 Task 이슈로 등록, `feature/<에픽번호>-<설명>` 브랜치 생성
   - Task 이슈 생성 직후, 에픽 이슈의 해당 체크리스트 줄을 일반 텍스트가 아니라 `- [ ] #<Task 이슈번호>`로 교체한다 (GitHub가 자동 링크 + 이슈 종료 시 체크박스 자동 완료 처리)
3. 작은 단위로 커밋
4. PR 생성 전 `git merge origin/main`으로 최신 `main`을 로컬에 먼저 동기화한다 — 에픽 하위 작업(예: 1라운드 3개 태스크)이 여러 워크트리에서 병렬로 진행 중이면, 리뷰·재작업으로 브랜치가 오래 열려 있는 동안 다른 태스크가 먼저 머지돼 같은 파일(화면 진입점, `CLAUDE.md` 등)에서 충돌이 생기기 쉽다. 이미 PR을 올린 뒤 충돌이 발견돼도 같은 방법(로컬 merge)으로 해결하고 다시 push한다.
4-1. 커밋·PR 전 로컬에서 CI와 동일한 린트를 둘 다 통과시킨다: `swiftlint lint --strict`와 `swiftformat --lint .` — CI `lint.yml`이 둘을 순서대로 돌리므로, swiftlint만 확인하고 올리면 SwiftFormat(`wrapFunctionBodies` 등)에서 실패한다. 자동 수정은 `swiftformat .` 후 다시 `--lint`로 검증한다.
5. PR 생성 (PR 템플릿 사용, `Closes #이슈번호`로 연결)
6. 리뷰 후 **Squash merge**
7. 머지 후 브랜치 삭제

## 머지 전략
PR은 기본적으로 **Squash merge**를 사용한다. main 브랜치의 히스토리를 기능 단위로 유지하기 위함이다.

## 충돌 해결
두 브랜치가 같은 파일의 서로 다른 관심사를 수정해 충돌하면(예: 한쪽은 화면의 바깥 레이아웃 구조를, 다른 쪽은 안쪽 콘텐츠 로직을 수정), 한쪽 브랜치를 통째로 선택하지 말고 두 변경을 구조적으로 합친다(바깥 구조는 A, 안쪽 로직은 B처럼). 병합 후에는 반드시 빌드+테스트+스크린샷으로 두 기능이 함께 정상 동작하는지 재확인한다 — 충돌 마커를 지운 것만으로는 두 기능의 조합이 실제로 맞물려 동작하는지 보장되지 않는다.

## 한 작업을 여러 타입 커밋으로 쪼갤 때
`docs` / `feat` / `fix`처럼 타입을 나눠 커밋해야 하는데 변경이 이미 한 워킹 트리에 섞여 있으면, 이 환경에서는 `git add -p`/`-i`(대화형)를 쓸 수 없다. 최종본을 스크래치패드에 복사해두고 → 앞 커밋 시점의 파일 상태를 직접 만들어 커밋 → 최종본을 복원해 다음 커밋, 순서로 진행한다. 중간 상태에서도 `build_sim`을 돌려 **각 커밋이 독립적으로 빌드되는지** 확인한다(히스토리 이분 탐색이 가능해야 한다).

계획(`ax:write-plans`) 단계에서 "태스크 N까지는 커밋 1, 태스크 M부터는 커밋 2"처럼 미리 커밋 경계를 정할 때는, 그 경계가 걸치는 타입의 시그니처 변경(예: `View`의 `init`에 기본값 없는 파라미터 추가)이 없는지 먼저 확인한다 — 기본값 없는 파라미터를 추가하면 그 타입의 **모든 호출부**가 같은 커밋에 함께 들어가야 독립 빌드가 성립하는데, 호출부 수정이 다음 커밋(다음 태스크)에 배정돼 있으면 경계에서 빌드가 깨진다. 커밋을 쪼개려고 임시 기본값(`= false`, `= {}` 등)을 영구 코드에 남기는 절충은 하지 않는다 — 이럴 땐 계획의 커밋 경계가 잘못된 것이니 실제 diff 확정 후 재조정하거나 하나의 커밋으로 합친다.

## Push 권한
`git push`는 `.claude/settings.json`의 permission deny 목록(`Bash(git push *)`)으로 의도적으로 막혀 있다 — 원격에 영향을 주는 작업이라 사용자가 직접 실행하게 한다. 매번 "막혀 있다"고 재설명하지 말고, 실행 가능한 명령어(`! git push -u origin <branch>`)만 바로 제시한다.
